# Recipe: other batch operations

Placeholders as in `references/workflows/batch-operation.md`. Add these only when the user asks for them; batch-void in the reference service is the only batch generated by example.

## When to use

- The user asks to create, update, delete, or run another existing domain command on many aggregates in one request: batch-create, batch-update, batch-delete, batch-`<command>` (design §9.2 lists the first three as recipes).
- The single operation must exist first (create and delete come with the aggregate; a domain command comes from `references/workflows/domain-command.md`). The batch reuses its permission.
- Every form keeps the batch-void contract: `{"items": [...]}` with at most `MAX_BATCH_ITEMS` (100) items, one locked load or one insert, one flush, partial success reported as 207, and the fallback to one unit of work per item on an unexpected failure (design §8.2, §9.4).

## Files to change

The same files as `references/workflows/batch-operation.md`:

- `app/core/<context>/use_case/<aggregate>_use_case.py`: `create_many`, `update_many` (with `update_with`), `delete_many` or `<command>_many`.
- `app/adapter/controller/<context>/<aggregate>_controller.py`: the matching method through `run_batch`.
- `app/port/restful/<context>/<aggregate>_schemas.py`: the item and request models.
- `app/adapter/controller/<context>/<aggregate>_commands.py`: for batch-update, one `Update<Aggregate>Command` per item.
- `app/port/restful/<context>/<aggregate>_router.py`: `POST /<aggregates>/batch-create`, `/batch-update`, `/batch-delete` or `/batch-<command>`.
- `tests/adapter/test_<aggregate>_controller.py`, `tests/port/test_<aggregate>_api.py`.

## Steps

1. Batch-`<command>`: follow `references/workflows/batch-operation.md` unchanged with the other command's domain method.
2. Batch-create, use case: `async def create_many(self, organization_id: UUID, items: Sequence[BatchItem[<Aggregate>Id, <Aggregate>Content]], doer: User) -> BatchResult[<Aggregate>Id, <Aggregate>]` returning `await create_batch(self._repository, items, lambda aggregate_id, content: <Aggregate>.<factory>(id=aggregate_id, organization_id=organization_id, content=content, doer=doer))` from `fast_ddd.batch`. Each item's `DomainError` from the factory is recorded per item; `create_batch` saves the rest with one `save_many`.
3. Batch-create, controller: `create_many(items: Sequence[BatchItem[<Aggregate>Id, <Aggregate>Content]])` takes the items with their final ids, takes `organization_id` as `create` does (raise `TenantContextMissingError` when it is `None`), calls `run_batch(items, batch=lambda batch: self._use_case.create_many(organization_id, batch, doer), ...)` and passes `single=lambda item: self._use_case.issue(item.id, organization_id, item.payload, doer)` (the single create). A client id that already exists makes the whole-batch insert fail; the fallback then reports that item as 409 `<context>.<aggregate>.already_exists` and creates the others.
4. Batch-create, port (`ensure_unique_ids` and `batch_response` from `fast_ddd_port.http`, `run_batch` from `fast_ddd_adapter.controller`): items have no `etag` (`expected_version=None`); an optional client `id` follows the single create's rule. Build every `BatchItem(<Aggregate>Id(item.id or new_id()), <content>)` here first (`new_id` from `fast_ddd.aggregate`), then call `ensure_unique_ids` on all their ids: generated ids never collide, so only repeated client ids are reported, at their own request index. The port then holds the same ids as the outcome; `batch_response(items, outcome, <Aggregate>Response.from_domain, success_status=201)` looks each result up by `item.id`.
5. Batch-update, use case: the merge of omitted fields needs the locked current state, and `UNSET` must not reach core. Give each item a function from the current content to the new one: `type <Aggregate>Change = Callable[[<Aggregate>Content], <Aggregate>Content]` in the use case module, `update_many(items: Sequence[BatchItem[<Aggregate>Id, <Aggregate>Change]], doer)` returning `await apply_batch(self._repository, <Aggregate>, items, lambda aggregate, change: aggregate.update(change(aggregate.content), doer))`, and a single `update_with(<aggregate>_id, change, expected_version, doer)` that loads with the lock, checks the version and applies the same call.
6. Batch-update, controller and port: the controller turns each item's `Update<Aggregate>Command` into a change function that applies `merge(command.<field>, current.<field>)` for every field, exactly as the single `update` does, and calls `run_batch(items, batch=lambda batch: self._use_case.update_many(batch, doer), single=lambda item: self._use_case.update_with(item.id, item.payload, item.expected_version, doer))`. Items are `BatchUpdate<Aggregate>Item(RequestModel)` with `id`, `etag` and the PATCH fields of `Update<Aggregate>Request` (same `MISSING` handling per item); return `batch_response(items, outcome, <Aggregate>Response.from_domain)`.
7. Batch-delete, use case: `delete_many` returns `await apply_batch(self._repository, <Aggregate>, items, lambda aggregate, _: aggregate.delete(doer))` with `P = None`. `run_batch` needs a `single` that returns the aggregate, so have the single `delete` use case method return the deleted aggregate (or add one that does) and pass it as `single`.
8. Batch-delete, port: items carry `id` and `etag` like batch-void; return `batch_response(items, outcome, <Aggregate>Response.from_domain, success_status=204)`, which writes no `data` for successful items.
9. Write the tests, then `make check`.

## Required tests

- The tests of `references/workflows/batch-operation.md` for each new batch: equal statement counts for N=1 and N=50 (`test_batch_void_round_trips_do_not_grow_with_the_batch` in `references/example/tests/adapter/test_invoice_controller.py`), per-item results in request order (`test_batch_void_reports_each_item` in `references/example/tests/port/test_invoice_api.py`), duplicate and oversized requests rejected with 422 (`test_batch_void_rejects_duplicates_and_oversized_batches`), and 403 without the single operation's permission.
- Batch-create: successful items are 201 with `data` and `etag`; an item whose client id already exists is 409 `already_exists` while the others are created; a factory `DomainError` fails only its item.
- Batch-update: omitted fields keep their value and `null` clears an Optional field, per item, as for the single PATCH; a stale `etag` fails only its item with 412.
- Batch-delete: successful items are 204 without `data` and the rows are gone; a stale `etag` is 412 and a missing or other-organization id is 404, per item.

## Pitfalls

- Never replace a batch with a bulk SQL `INSERT`, `UPDATE` or `DELETE`; it skips domain rules, events and archive snapshots.
- Do not loop over the single controller method; that is one unit of work per item and the round trips grow with N.
- Non-HTTP callers of any batch follow step 5 of `references/workflows/batch-operation.md`: one chunk of at most `BULK_CHUNK_SIZE` ids per unit of work.
